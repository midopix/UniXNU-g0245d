## 一、先钉死一个几何事实：L1 index 3 是对的

v186 的 loader 截图给出决定性证据：

```
WINDOW 0x38000000   ENTRY PA 0x95419488
```

`ENTRY − Base = 0x415488`（entry 相对内核基址的偏移，可由链接脚本确定），因此

```
内核基址 PA = 0x95419488 − 0x415488 = 0x95004000
0x95004000 >> 30 == 2
```

`create_bootstrap_mapping()` 把内核自己的 L2 表描述符放在 **L1 index 2**。
所以 `start.s` 把面板窗口放在 **L1 index 3** 是唯一正确选择，`start.s` 的原始注释
（"cannot reuse the kernel window's index 2 … kernel PA 0x95400000"）本来就没错。

> **作废记录**：2026-11-17 17:00–17:20 曾有一版"把窗口搬到 L1 index 2"的 v187 实验，
> 依据是"L1[3] 与别的东西自撞"。该前提是错的——搬到 index 2 会直接覆盖内核自己的
> 表描述符。整版已 `git apply --reverse` 回退，旧补丁存于
> `workspace/tmp/parked/zzz-v187-l1idx2-SUPERSEDED.patch`。
> 教训：**先用实机打印出来的 PA 算一遍 index，再动手改页表。**

## 二、三个"无条件执行"的混淆源

v168 之后每次启动的真实终点，都不是映射失败，而是下面三段代码：

| # | 位置 | 干了什么 | 后果 |
|---|---|---|---|
| 1 | `osfmk/arm/arm_init.c` `g0245d_fb_blackout()` | 刷黑整屏 6,220,800 字节 + `dc civac` | 抹掉此前所有诊断带，屏幕变纯黑 |
| 2 | `osfmk/arm/arm_init.c` `g0245d_fbcon_start()` | 在 `arm_init()` 窗口调 `ml_io_map` | `io_submap` 由 `STARTUP(KMEM, STARTUP_RANK_LAST, io_map_init)` 建立，此时还不存在 → 拿到坏映射；且它正好夹在 `fb_mark(2)` 与 `fb_mark(3)` 之间，所以"看着像死在 mark 2 和 3 之间" |
| 3 | `osfmk/kern/startup.c` | `2000 × (mmss_recover + 2e6 次忙等)` 然后 `g0245d_halt()`（`msr daifset,#0xf; 1: b 1b`） | 内核自己永久自旋。**这才是每次启动的真正终点** |

另外确认一条：`ml_io_map()` **永不返回 0**（`io_map.c` 只有一个
`return start + start_offset`，且 `kmem_alloc` 用 `KMA_NOFAIL`）。
所以历史上所有 `if (map != 0)` / `== NULL` 的守卫都是**死守卫**，
它们"通过"了，但映射内容根本不可用。

## 三、v187 / v188 做了什么

**v187 `zzz-g0245d-v187-drop-confounders.patch`** —— 只拆，不加：
- 注释掉 `arm_init.c` 里的 `g0245d_fb_blackout()` 与 `g0245d_fbcon_start()`
- `#if 0` 包住 `startup.c` 的 2000× 自冻块与 `g0245d_halt()`
- **`start.s` 一行未动**（L1[3] 保持不变）

实机判读（照片像素分析）：PAINT 8..12 五条全在；fb 行 184–631 连续 448 行白
（证明内核活着走进 `arm_init:660` 的 flood）；`fb_blackout` 确认没再擦屏。
结论：拆对了，但**条带法到此为止**——fb 700–955 是交接前六条白条与交接后
`fb_mark(1..6)` 的重叠区，天生无法区分。必须转向文本 console。

**v188 `zzz-g0245d-v188-fbcon-lockdown-text.patch`** —— 挂上文本 console：
1. `g0245d_fbcon_start()` 从 `arm_init()` 挪到 `startup.c`，
   紧跟 `kernel_startup_initialize_upto(STARTUP_SUB_LOCKDOWN)` 之后
   —— 那时 `io_map_init` 已跑，`ml_io_map()` 才有效
2. 打开 `serial_console_enabled = true` + `switch_to_serial_console()`，
   让后续 `kprintf()`/`printf()` 全部落到屏上
3. `G0245D_FBCON_ROW0` 由 `40` 改为 `960`：40 落在 fb 行 1303..1895
   （标定区外，永远看不见），960 落在 fb 行 384..959
   （在已证明可见的 8..972 之内）

**顺序安全性已核对**：`serial_console_enabled` 是 `SECURITY_READ_ONLY_LATE`，
v188 在 `startup.c:912` 写它，而 `machine_lockdown()` 在 `startup.c:934` 执行
——写在 lockdown **之前**，不会触发只读保护。

## 四、构建链两个新坑（都会让构建"秒退"）

1. **toolchain 里的 `git` 会劫持 git**
   `toolchain-root/usr/bin/git` 是 deb 解包产物，`--exec-path` 指向本机不存在的
   `/usr/lib/git-core`，于是 `unixnu build kernel` 第一步就报
   `git: 'submodule' is not a git command`。
   解法：把宿主 git 的软链放在 toolchain 之前：

   ```sh
   export PATH="$D/workspace/tmp/gitshim:$D/workspace/tmp/toolchain-root/usr/bin:$PATH"
   ```

2. **`patches/xnu/series` 是硬校验**
   `unixnu` 按 series 逐条校验文件存在，缺一个就直接 `patch missing:` 中止；
   同时 `build-xnu-4k-baseline.sh` 又按 `patches/xnu/*.patch` 通配重放一遍。
   所以：**落补丁 + 登记 series 必须同时做**；停用的补丁要注释掉登记行并写明
   PARKED 理由，否则下一次构建必挂。
